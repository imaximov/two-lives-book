# Процесс перевода

Этот документ — рабочая инструкция. Любой агент (Claude, GPT, Gemini …) или человек, который переводит,
ревьюит или правит текст, **читает его целиком перед началом работы**. Принятые решения, на которые
здесь есть ссылки, лежат в [`translation/decisions.md`](../translation/decisions.md).

## 1. Цель и принципы

Сделать английский (затем польский) текст «Двух жизней», который:

1. **Точен.** Без пропусков, добавлений и «пересказа своими словами». Эзотерические понятия
   передаются одинаково на протяжении всех ~900 тыс. слов.
2. **Читается как литература**, а не как калька. Голос рассказчика (Лёвушка, пожилой человек вспоминает
   юность), речь Учителей и бытовые диалоги звучат по-разному.
3. **Последователен.** Один термин — один перевод. Одно имя — одно написание. Одинаковые обращения.

Как этого добиваемся:

- **Для английского основа — старый перевод** (решение DEC-003). Мы его редактируем, а не выбрасываем:
  сохраняем верное, исправляем ошибки. Заново переводим только то, чего в нём нет.
- **Глоссарий, персонажи и стайлгайд обязательны** и читаются перед каждым заходом.
  Самодеятельность в терминах запрещена (§9).
- **Правит и переводит одна модель, ревьюят другие.** Внешние ревьюеры запускаются владельцем вручную
  на контрольных точках (§7).
- **Всё, что проверяется скриптом, проверяется скриптом**, а не глазами.
- **Решения записываются.** Спорное место решается один раз, фиксируется в `translation/decisions.md`
  и дальше применяется везде.
- **Последнее слово за владельцем** по ключевой терминологии и стилю.

Польский переводим **с русского оригинала**, а не с английского: языки близки, двойной перевод копит
искажения. Готовый английский служит вспомогательным справочником.

## 2. Два режима работы

| Режим | Где | Что делаем |
|---|---|---|
| **Редактура** | EN: часть I, часть II, часть III гл. 1–9 (и всё, что найдётся из новых версий старого перевода) | Берём выровненный по абзацам старый перевод и доводим его до стандарта: исправляем ошибки смысла, пропуски, нарушения глоссария, мешающие кальки |
| **Перевод** | EN: часть III с гл. 10, часть IV. PL: всё | Переводим с русского с нуля, **в голосе отредактированного английского текста** (для EN) |

Главный принцип редактуры: **не переписывать ради переписывания.** Верное и естественно звучащее
остаётся как есть. Насколько глубоко вмешиваться, определяет стайлгайд по итогам анализа старого
перевода (PLAN, этап 2). Каждая правка видна в git-диффе: первым коммитом старый текст импортируется
как есть, дальше идут только наши изменения.

## 3. Роли

| Роль | Кто | Отвечает за |
|---|---|---|
| **Владелец** | человек (хозяин репо) | ключевые термины и стиль, одобрение пилота, ответы на `queries`, **запуск внешних ревью**, финальное «публикуем» |
| **Переводчик / редактор текста** | Claude (сессия Claude Code) | редактура или перевод главы, предложения в глоссарий, вопросы, синопсис, **подготовка запросов на ревью** |
| **Проверки** | скрипты `tools/` | структура, длины, глоссарий, имена, типографика |
| **Внешние ревьюеры** | модели других вендоров, запускает владелец | независимое сравнение RU ↔ EN/PL, структурированные замечания |
| **Разбор замечаний** | Claude, по возможности **новая сессия** (свежий контекст) | принять или отклонить каждое замечание с причиной, внести правки |
| **Вычитчик** | человек, носитель языка (желательно) | чтение на preview-сайте как книги, сообщения об ошибках |

## 4. Стадии главы (`translation/status.yml`)

```
[legacy-imported] → draft → checked → reviewed → edited → proofread → published
```

| Стадия | Критерий перехода |
|---|---|
| `source-ready` (RU) | русская глава извлечена, сверена с PDF, ID проставлены, **заморожена** (хеш записан) |
| `legacy-imported` | только в режиме редактуры: старый перевод импортирован **без правок** и выровнен по ID абзацев оригинала |
| `draft` | редактура или перевод всех абзацев готовы, синопсис главы записан |
| `checked` | `npm run check` без ошибок, предупреждения разобраны |
| `reviewed` | получен минимум один отчёт внешнего ревью (для пилота и «тяжёлых» глав — два) |
| `edited` | все замечания разобраны в `resolution.md`, правки внесены, `check` снова зелёный |
| `proofread` | человек прочитал главу на preview, ошибки исправлены |
| `published` | владелец одобрил, глава видна на основном сайте |

Пример `status.yml`:

```yaml
p1-c01:
  ru: { stage: source-ready, hash: 3f9a… }
  en: { stage: reviewed, mode: revision, reviewers: [openai-<model>, google-<model>], updated: 2026-10-05 }
  pl: { stage: none }
```

## 5. Подготовка перед заходом (обязательный чек-лист агента)

Перед работой над главой `pX-cYY` на языке `LANG`:

1. Прочитать `AGENTS.md` и этот документ.
2. Прочитать `translation/decisions.md` (он короткий).
3. Прочитать `translation/style/LANG.md` целиком.
4. Получить глоссарий и персонажей для главы: `npm run glossary pX-cYY LANG`. Пока скрипта нет —
   прочитать `translation/glossary.yml` и `translation/characters.yml` целиком.
5. Прочитать `translation/synopsis/part-X.md` до текущей главы: кто есть кто, что уже произошло.
6. Прочитать последние ~20 абзацев предыдущей главы на `LANG`, чтобы не сломать голос и связку.
7. Проверить `translation/queries/LANG/` на ответы владельца по этой главе.

## 6. Работа над главой

### 6.1. Общие правила (оба режима)

1. Работать **кусками по 1 500–2 500 слов оригинала**, по границам абзацев (главы бывают от 2 до 18 тыс. слов).
   Перед каждым куском держать в контексте предыдущий готовый кусок.
2. Для каждого абзаца `{#id}` оригинала — абзац с тем же `{#id}`. Ничего не пропускать, не склеивать,
   не добавлять пояснений в текст. Пояснение, если оно действительно нужно, выносится в сноску, и только
   если так разрешено в стайлгайде.
3. Термины и имена — **строго** по глоссарию и `characters.yml` (§9). Новый термин → запись со
   `status: proposed`, а не молчаливая импровизация.
4. Тёмное место, двусмысленность, возможная опечатка в оригинале → вопрос в
   `translation/queries/LANG/pX-cYY.md` с ID абзаца, цитатой, вариантами и рекомендацией.
   В тексте оставить лучший вариант, **не** ставить заглушку.
5. После главы:
   - `npm run check` → исправить ошибки, разобрать предупреждения;
   - дописать синопсис главы в `translation/synopsis/part-X.md`;
   - обновить `status.yml`;
   - коммит (§12).

### 6.2. Режим «Редактура»

Для каждого абзаца сравнить старый перевод с оригиналом и:

- **оставить**, если смысл верен, термины по глоссарию и текст читается естественно;
- **исправить** ошибку смысла, пропуск или добавление, нарушение глоссария (например, *duke* → *prince*),
  кальку, которая мешает читать, грамматическую ошибку;
- **не трогать** вкусовые мелочи, если они не противоречат стайлгайду.

Если абзац приходится переписать почти целиком, это нормально, но стоит отметить в `resolution.md` главы
(строка «переписаны абзацы …»). Так владелец видит масштаб изменений. По git-диффу считается доля
изменённых абзацев — эта метрика показывает, не уходит ли редактура в переписывание.

### 6.3. Режим «Перевод»

С русского с нуля. Для английского — в голосе уже отредактированных частей: перед первой главой нового
перевода (часть III, гл. 10) проводится мини-пилот. Две-три страницы сравниваются с соседними
отредактированными главами, владелец одобряет.

## 7. Внешнее ревью и контрольные точки

Внешних ревьюеров **запускает владелец вручную** (DEC-005). Агент их не вызывает и API-ключей не имеет.

### 7.1. Протокол контрольной точки

Когда единица работы готова к ревью (анализ, глоссарий, глава, пачка глав), агент:

1. Прогоняет `npm run check`, коммитит и **пушит**.
2. Готовит **запрос на ревью** — файл `translation/reviews/<LANG>/<unit>/request.md`, тоже в коммите.
   В файле:
   - что ревьюим и зачем (цель, на что смотреть в первую очередь);
   - контекст: выдержка из стайлгайда, подмножество глоссария, при необходимости синопсис;
   - материал: таблица `ID | RU | EN` (для анализа и глоссария — соответствующий документ);
   - список **новых `proposed`-терминов** с контекстом: ревьюер подтверждает или возражает (для §9);
   - строгий формат ответа (§7.2).
   Большую главу делить на несколько запросов (`request-1.md`, `request-2.md`), чтобы каждый влез
   в окно модели.
3. **Останавливается** и пишет владельцу в чат:
   - что готово (ссылки на коммит и файлы);
   - **стартовый промпт** для ревьюера, готовый к копированию: кто ты, что ревьюим, цель, критерии,
     формат ответа, «файл запроса приложен ниже»;
   - сколько ревьюеров нужно (1 или 2) и на что обратить внимание.
4. Ждёт. Дальше работу по этой единице не продолжает.

Владелец отдаёт промпт и файл запроса внешней модели и приносит ответ: вставляет в чат или кладёт файлом
`translation/reviews/<LANG>/<unit>/<vendor>-<model>-<YYYYMMDD>.json` (или `.md`). Если ответ вставлен
в чат, агент сам сохраняет его в этот путь.

### 7.2. Формат замечаний

JSON (можно внутри блока кода в ответе модели):

```json
{
  "unit": "p1-c05",
  "lang": "en",
  "reviewer": "google-<model>",
  "findings": [
    {
      "id": "p1-c05-042",
      "category": "omission",
      "severity": "major",
      "source_excerpt": "…но не мог сказать ни слова",
      "target_excerpt": "…but said nothing",
      "suggestion": "…but could not utter a single word",
      "rationale": "‘не мог’ — невозможность, а не выбор; в переводе смысл изменён"
    }
  ],
  "terms": [
    { "term_id": "samoobladanie", "verdict": "agree" },
    { "term_id": "dacha", "verdict": "object", "suggestion": "country house", "rationale": "…" }
  ],
  "overall": { "accuracy": 4, "fluency": 4, "style": 3, "comment": "…" }
}
```

Категории (упрощённый MQM): `mistranslation`, `omission`, `addition`, `terminology`, `name`,
`fluency`, `style`, `register`, `grammar`, `typography`.
Серьёзность: `critical` (искажён смысл, пропущено важное), `major` (заметная неточность или корявость),
`minor` (вкусовое, мелочь).

### 7.3. Сколько ревьюеров

- **Анализ старого перевода, глоссарий v0, пилот и главы с плотными духовными беседами**
  (поучения Учителей): два разных вендора.
- **Остальное**: один вендор, выборочно второй на каждую пятую главу.
- Метрика — число `critical + major` на 1 000 слов. Растёт → усиливаем ревью и правим стайлгайд.
  Стабильно низкая → можно ревьюить пачками по несколько глав.

## 8. Разбор замечаний

По возможности **в новой сессии** (свежий контекст) после той же подготовки (§5).

1. Свести все отчёты по единице (`npm run review:merge`, пока его нет — вручную) и склеить дубликаты.
2. По каждому замечанию — решение в `translation/reviews/LANG/<unit>/resolution.md`:
   `accept` (правка внесена) / `accept-modified` (правка по-своему) / `reject` + причина одной строкой.
3. Если принятое замечание касается термина или стиля, обновить глоссарий или стайлгайд и
   **проверить другие главы** (`grep`) на ту же проблему.
4. Обработать вердикты по терминам (§9, вариант Б).
5. Отклонённое `critical` или несогласие двух ревьюеров по смыслу → в `queries` владельцу.
6. `npm run check`, затем `status.yml` → `edited`, коммит.

## 9. Глоссарий и персонажи — никакой самодеятельности

Принятая схема утверждения — **вариант Б** (DEC-002).

### 9.1. Уровни терминов

| Уровень | Что входит | Кто утверждает |
|---|---|---|
| `core` | понятия учения («Учитель», «Община», «Белое Братство», «Светлые Братья», «самообладание», «радость», «мир вам»…), имена персонажей, титулы («князь», «лорд», «сэр»), формы обращения, повторяющиеся формулы благословения и приветствия | **только владелец** |
| `secondary` | бытовые реалии, топонимы, предметы, эпизодические персонажи, устойчивые бытовые выражения | **автоматически**: если на контрольной точке ни один внешний ревьюер не возразил (`verdict: agree` или термин без замечаний). Возражение или расхождение ревьюеров → владельцу |

Сомневаешься, какой уровень, — ставь `core`.

### 9.2. Правила

1. **Утверждённое (`approved`) обязательно.** Менять его может только владелец. Замена идёт скриптом
   по всему корпусу и записывается в `decisions.md`.
2. **Первый вариант держится.** Пока `proposed`-термин не утверждён, все агенты и главы используют именно
   его. Второй вариант того же русского слова появиться не может, это ловит проверка.
3. **Дубли запрещены.** Две записи с одной русской леммой (например, из параллельных сессий) — ошибка
   проверки. Её нужно свести до коммита.
4. **Каждая новая запись с контекстом:** `first_seen` (ID абзаца) и `note`, почему выбран вариант.
5. **Разбор пачкой.** На каждой контрольной точке `npm run glossary --proposed` выдаёт таблицу новых
   терминов. `secondary` утверждаются по вердиктам ревьюеров, `core` уходят владельцу одним списком.
6. **Для английского по умолчанию берётся вариант из старого перевода**, если он не ошибочен. Его
   фиксируем в поле `en_legacy` — видно, где мы отошли от старого перевода и почему.

### 9.3. `translation/glossary.yml`

```yaml
- id: knyaz
  ru: князь                         # лемма
  ru_forms: [князь, князя, князю, князем, князе, князья, князей]
  en: prince                        # текущий вариант
  en_legacy: duke                   # как было в старом переводе
  en_avoid: [duke]                  # запрещённые варианты (ловятся проверкой)
  pl: książę
  tier: core                        # core | secondary
  status: approved                  # proposed | approved | rejected
  approved_by: owner                # owner | review
  note: Князь — prince (русский титул); duke — это герцог
  first_seen: p1-c16-003
  decided: DEC-0xx
```

### 9.4. `translation/characters.yml`

```yaml
- id: levushka
  ru: Лёвушка                       # Лев Николаевич, рассказчик частей I и III
  en: Levushka                      # proposed
  en_legacy: Levushka               # сверить со старым переводом
  pl: Lowuszka                      # proposed, уточнить у носителя (Liowuszka?)
  gender: m
  role: narrator
  address: {to_I: "вы", I_to_him: "ты"}   # важно для польского (ty / Pan) и для тона в EN
  tier: core
  first_seen: p1-c01-001
```

### 9.5. Известные вопросы (решаются на этапах анализа и глоссария)

| Вопрос | Старый перевод | Проблема | Рекомендация |
|---|---|---|---|
| «И.» (Иллофиллион) | «I.», «with I.», «I.'s» | сливается с местоимением *I* | «Il.» или полное «Illofillion», решить |
| князь | *duke* (≈300 раз в части I) | ошибка: duke — это герцог | **prince** |
| Жанна | *Joan* | героиня француженка | **Jeanne** |
| Инициалы мест: «в К.», «в Б.», «капитан Т.» | сохранены | стиль эпохи | сохранить |
| Вариант английского | британский с оксфордским *-ize* (colour, honour, grey, theatre, но recognize) | — | предварительно — так же (DEC-004), окончательно после анализа |
| Ты/вы | теряется | — | в EN передавать тоном и лексикой; в PL — *ty / Pan, Pani* по `characters.yml` |
| Кавычки в диалогах | “…” | RU — тире | EN — “…”; PL — решить в стайлгайде |

## 10. Синопсис — память проекта

`translation/synopsis/part-N.md` — краткое содержание по главам (на русском или английском).
Даёт агенту контекст, не заставляя читать предыдущие 300 тыс. слов. Пишется после каждой главы.
Формат: заголовок главы, 5–10 предложений, список «новые персонажи / понятия» с ID абзацев первого
появления.

## 11. Как работать с разными моделями

- **Редактирует и переводит одна модель на язык** (Claude), чтобы голос был ровным. Модель не меняем
  посреди части без повторной калибровки на пилотных главах.
- **Ревьюеры — модели других вендоров**, запускает владелец. Каждой даём один и тот же запрос и одну
  схему ответа, чтобы результаты сравнивались.
- Промпты лежат в `translation/prompts/` и версионируются. Меняли промпт — отмечаем в `decisions.md`.
- Никаких ключей API в репозитории.

## 12. Коммиты и ветки

- **Без трейлеров соавторства** (`Co-Authored-By` и подобных) — DEC-006.
- Сообщения: `en: import legacy p1`, `en: p1-c05 revision`, `en: p1-c05 review fixes`,
  `glossary: князь → prince (approved)`, `ru: p1-c05 fix typo from PDF check`, `review: p1-c05 request`.
- Одна глава на одном языке — один коммит (или ветка или PR `en/p1-c05`, когда появится preview-сайт).
- Перед контрольной точкой — обязательно push (§7.1).

# Процесс перевода

Этот документ — рабочая инструкция. Любой агент (Claude, GPT, Gemini …) или человек, который переводит,
ревьюит или правит текст, **читает его целиком перед началом работы**.

## 1. Цель и принципы

Перевести «Две жизни» с русского на английский, затем на польский так, чтобы текст:

1. **Был точным.** Без пропусков, добавлений и «пересказа своими словами». Эзотерические понятия
   передаются одинаково на протяжении всех ~900 тыс. слов.
2. **Читался как литература** на целевом языке, а не как калька. Голос рассказчика (Лёвушка, пожилой
   человек вспоминает юность), речь Учителей и бытовые диалоги звучат по-разному.
3. **Был последовательным.** Один термин — один перевод. Одно имя — одно написание. Одинаковые обращения.

Как этого добиваемся:

- **Глоссарий, персонажи и стайлгайд обязательны** и читаются перед каждым заходом.
- **Перевод делает одна модель, ревью — другие.** Независимый взгляд ловит то, что автор перевода не видит.
- **Всё, что проверяется скриптом, проверяется скриптом**, а не глазами.
- **Решения записываются.** Спорное место решается один раз, фиксируется в `translation/decisions.md`
  и дальше применяется везде.
- **Последнее слово за владельцем проекта** по терминологии и стилю; финальная вычитка — за человеком.

Польский переводим **с русского оригинала**, а не с английского: языки близки, двойной перевод копит
искажения. Готовый английский служит вспомогательным справочником.

## 2. Роли

| Роль | Кто | Отвечает за |
|---|---|---|
| **Владелец** | человек (хозяин репо) | решения по глоссарию и стилю, одобрение пилота, ответы на `queries`, финальное «публикуем» |
| **Переводчик** | Claude (сессия Claude Code) | черновик главы, предложения в глоссарий, вопросы, синопсис главы |
| **Проверки** | скрипты `tools/` | структура, длины, глоссарий, имена, типографика |
| **Ревьюеры** | другие модели (GPT, Gemini, …) | независимое сравнение RU ↔ перевод, структурированные замечания |
| **Редактор** | Claude, **новая сессия** (не та, что переводила) | разбор замечаний: принять или отклонить с причиной, внести правки |
| **Вычитчик** | человек, носитель языка (желательно) | чтение на preview-сайте как книги, сообщения об ошибках |

## 3. Стадии главы (`translation/status.yml`)

```
source-ready → draft → checked → reviewed → edited → proofread → published
```

| Стадия | Критерий перехода |
|---|---|
| `source-ready` | русская глава извлечена, сверена с PDF, ID проставлены, **заморожена** (хеш записан) |
| `draft` | перевод всех абзацев готов, синопсис главы записан |
| `checked` | `npm run check` без ошибок, предупреждения разобраны |
| `reviewed` | есть минимум один отчёт кросс-вендорного ревью (для пилота и «тяжёлых» глав — два) |
| `edited` | все замечания разобраны в `resolution.md`, правки внесены, `check` снова зелёный |
| `proofread` | человек прочитал главу на preview, ошибки исправлены |
| `published` | владелец одобрил, глава видна на основном сайте |

Пример `status.yml`:

```yaml
p1-c01:
  ru: { stage: source-ready, hash: 3f9a… }
  en: { stage: reviewed, reviewers: [openai-<model>, google-<model>], updated: 2026-10-05 }
  pl: { stage: none }
```

## 4. Подготовка перед заходом (обязательный чек-лист агента)

Перед переводом или правкой главы `pX-cYY` на язык `LANG`:

1. Прочитать `AGENTS.md` и этот документ.
2. Прочитать `translation/style/LANG.md` целиком.
3. Получить глоссарий и персонажей для главы: `npm run glossary pX-cYY LANG`. Пока скрипта нет —
   прочитать `translation/glossary.yml` и `translation/characters.yml` целиком.
4. Прочитать `translation/synopsis/part-X.md` до текущей главы: кто есть кто, что уже произошло.
5. Прочитать `translation/decisions.md` (он короткий).
6. Прочитать последние ~20 абзацев перевода предыдущей главы, чтобы не сломать голос и связку.
7. Проверить `translation/queries/LANG/` на ответы владельца по этой главе.

## 5. Перевод главы (роль «Переводчик»)

1. Работать **кусками по 1 500–2 500 слов оригинала**, по границам абзацев (главы бывают от 2 до 18 тыс. слов).
   Перед каждым куском держать в контексте предыдущий переведённый кусок.
2. Для каждого абзаца `{#id}` оригинала выдать абзац с тем же `{#id}`. Ничего не пропускать, не склеивать,
   не добавлять пояснений в текст. Пояснение, если оно действительно нужно, выносится в сноску, и только
   если так разрешено в стайлгайде.
3. Термины и имена — строго по глоссарию и `characters.yml`. Если встретился новый термин или устойчивое
   выражение, которое ещё повторится, **не выдумывать молча**:
   - выбрать лучший вариант и использовать его;
   - добавить запись в `translation/glossary.yml` со `status: proposed` и контекстом (ID абзаца).
4. Тёмное место, двусмысленность, возможная опечатка в оригинале → вопрос в
   `translation/queries/LANG/pX-cYY.md` с ID абзаца, цитатой, вариантами и рекомендацией.
   В тексте оставить лучший вариант, **не** ставить заглушку.
5. После главы:
   - `npm run check` → исправить ошибки, разобрать предупреждения;
   - дописать синопсис главы в `translation/synopsis/part-X.md`: 5–10 предложений, новые персонажи,
     важные события и понятия;
   - обновить `status.yml` → `draft` или `checked`;
   - коммит: `en: p1-c05 draft` (одна глава — один коммит или PR).

## 6. Автоматические проверки (`npm run check`)

| Проверка | Уровень | Что ловит |
|---|---|---|
| Структура | ошибка | набор и порядок ID совпадает с оригиналом, нет пустых абзацев, шапка валидна, разметка блоков закрыта |
| Хеш источника | предупреждение | русская глава изменилась после перевода → перевод нужно сверить |
| Длина абзаца | предупреждение | отношение длины перевода к оригиналу вне коридора (для EN стартуем с 0,8–1,9 по символам, калибруем на пилоте) → возможный пропуск или добавление |
| Остатки | ошибка | кириллица в EN/PL тексте, `TODO`, `???`, `[…]` |
| Глоссарий | предупреждение | в оригинале есть форма термина, а в переводе нет утверждённого эквивалента; использован «запрещённый» вариант |
| Имена | предупреждение | написание имени не по `characters.yml`, похожие варианты (Levenshtein) |
| Типографика | предупреждение | прямые кавычки, `--` вместо тире, `...` вместо `…`, двойные пробелы; кавычки не того языка («» в EN, "" в PL) |

## 7. Кросс-вендорное ревью (роль «Ревьюер»)

### Как запускать

1. `npm run packet pX-cYY LANG` → `translation/packets/LANG/pX-cYY.md` (в `.gitignore`).
   В пакете: инструкция ревьюеру, выдержка из стайлгайда, подмножество глоссария, таблица
   `ID | RU | перевод`, **строгая JSON-схема ответа**. Большие главы делятся на несколько пакетов.
2. Владелец (или скрипт с API-ключами) отдаёт пакет модели другого вендора.
3. Ответ сохраняется как `translation/reviews/LANG/pX-cYY/<vendor>-<model>-<YYYYMMDD>.json`.

Пока скриптов нет, пакет можно собрать вручную по тем же правилам: инструкция из
`translation/prompts/review.md` плюс выровненный текст.

### Формат замечаний

```json
{
  "chapter": "p1-c05",
  "lang": "en",
  "reviewer": "google-<model>",
  "findings": [
    {
      "id": "p1-c05-042",
      "category": "omission",
      "severity": "major",
      "source_excerpt": "…но не мог сказать ни слова",
      "target_excerpt": "…but said nothing",
      "suggestion": "…but could not utter a single word",
      "rationale": "‘не мог’ — невозможность, а не выбор; в переводе смысл изменён"
    }
  ],
  "overall": { "accuracy": 4, "fluency": 4, "style": 3, "comment": "…" }
}
```

Категории (упрощённый MQM): `mistranslation`, `omission`, `addition`, `terminology`, `name`,
`fluency`, `style`, `register`, `typography`.
Серьёзность: `critical` (искажён смысл, пропущено важное), `major` (заметная неточность или корявость),
`minor` (вкусовое, мелочь).

### Сколько ревьюеров

- **Пилот (первые 3 главы) и главы с плотными духовными беседами** (поучения Учителей): два разных вендора.
- **Остальное**: один вендор, плюс выборочно второй на каждую пятую главу.
- Метрика — число `critical + major` на 1 000 слов. Растёт → усиливаем ревью и правим стайлгайд.
  Стабильно низкая → можно экономить.

## 8. Разбор замечаний (роль «Редактор»)

Выполняется **в новой сессии** (свежий контекст, не та, что переводила) после той же подготовки (§4).

1. `npm run review:merge pX-cYY LANG` сводит все отчёты и склеивает дубликаты замечаний от разных ревьюеров.
2. По каждому замечанию — решение в `translation/reviews/LANG/pX-cYY/resolution.md`:
   `accept` (правка внесена) / `accept-modified` (правка по-своему) / `reject` + причина одной строкой.
3. Если принятое замечание касается термина или стиля, обновить глоссарий или стайлгайд и
   **проверить другие главы** (`grep`) на ту же проблему.
4. Отклонённое `critical` или несогласие двух ревьюеров по смыслу → в `queries` владельцу.
5. `npm run check`, затем `status.yml` → `edited`, коммит `en: p1-c05 review fixes`.

## 9. Глоссарий и персонажи

### `translation/glossary.yml`

```yaml
- id: uchitel
  ru: Учитель                       # лемма
  ru_forms: [Учитель, Учителя, Учителю, Учителем, Учителе, Учителей, Учителям]
  en: Teacher                       # утверждённый вариант
  en_avoid: [Master, Guru]          # запрещённые варианты (ловятся проверкой)
  pl: Nauczyciel
  note: С заглавной, когда речь о Великих Учителях человечества; «учитель» в школе — со строчной
  status: approved                  # approved | proposed | rejected
  first_seen: p1-c02-015
  decided: 2026-10-03 (decisions.md#3)
```

Правила:

- `approved` менять может только владелец. Замена идёт через скрипт по всему корпусу и
  записывается в `decisions.md`.
- `proposed` — рабочий вариант переводчика. Им можно пользоваться, но владелец должен посмотреть
  (сводка — `npm run glossary --proposed`).
- В глоссарий идёт то, что **повторяется** или **критично по смыслу**: понятия учения
  («Община», «Белое Братство», «Светлые Братья», «самообладание», «радость», «мир вам»…), титулы
  («князь», «лорд», «сэр»), топонимы, устойчивые формулы обращения и благословения.

### `translation/characters.yml`

```yaml
- id: levushka
  ru: Лёвушка  # Лев Николаевич, рассказчик частей I и III
  en: Levushka      # proposed
  pl: Lowuszka      # proposed, уточнить у носителя (Liowuszka?)
  gender: m
  role: narrator
  address: {to_I: "вы", I_to_him: "ты"}   # важно для польского (ty / Pan) и для тона в EN
  first_seen: p1-c01-001
```

### Известные вопросы, которые нужно решить на пилоте

| Вопрос | Проблема | Варианты |
|---|---|---|
| «И.» (Иллофиллион) | в EN «with I.», «I.'s» сливается с местоимением *I* (так в старом переводе) | «Il.» / полное «Illofillion» / «I.» в особом начертании |
| князь | старый перевод: *duke* — ошибка | **prince** |
| Жанна | старый перевод: *Joan* | **Jeanne** (француженка) |
| Инициалы мест: «в К.», «в Б.», «капитан Т.» | стиль эпохи | сохранить инициалы как в оригинале |
| Британский или американский английский | действие в Лондоне, лорды, конец XIX века | рекомендация — **британская** орфография |
| Ты/вы | в EN теряется | передавать тоном и лексикой; в PL — *ty / Pan, Pani* по `characters.yml` |
| Кавычки в диалогах | RU — тире | EN — “…”; PL — тире (как в RU) или „…” — решить в стайлгайде |

## 10. Синопсис — память проекта

`translation/synopsis/part-N.md` — краткое содержание по главам (на русском или английском).
Даёт агенту контекст, не заставляя читать предыдущие 300 тыс. слов. Пишет переводчик после каждой главы.
Формат: заголовок главы, 5–10 предложений, список «новые персонажи / понятия» с ID абзацев первого
появления.

## 11. Как работать с разными моделями

- **Переводчик — одна модель на весь язык** (Claude), чтобы голос был ровным. Модель не меняем посреди
  части без повторной калибровки на пилотных главах.
- **Ревьюеры — модели других вендоров.** Каждой даём один и тот же пакет и одну схему ответа, чтобы
  результаты сравнивались.
- Промпты лежат в `translation/prompts/` и версионируются. Меняли промпт — отмечаем в `decisions.md`.
- Никакие ключи API в репозиторий не коммитим. Для автоматизации используем переменные окружения или
  секреты CI.

## 12. Коммиты и ветки

- Одна глава на одном языке — одна ветка или PR (`en/p1-c05`) либо один коммит, если работаем в общей ветке.
- Сообщения: `en: p1-c05 draft`, `en: p1-c05 review fixes`, `glossary: князь → prince (approved)`,
  `ru: p1-c05 fix typo from PDF check`.
- PR на главу даёт preview-ссылку: владелец и вычитчики читают там.

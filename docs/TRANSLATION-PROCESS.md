# Процесс перевода

Этот документ — рабочая инструкция. Любой агент (Claude, GPT, Gemini, Grok …) или человек, который
редактирует, переводит или ревьюит текст, **читает его целиком перед началом работы**. Решения, на которые
здесь есть ссылки, лежат в [`translation/decisions.md`](../translation/decisions.md).

## 1. Цель и принципы

Сделать английский (затем польский) текст «Двух жизней», который:

1. **Точен.** Без пропусков, добавлений и «пересказа своими словами». Эзотерические понятия
   передаются одинаково на протяжении всех ~900 тыс. слов.
2. **Читается как литература**, а не как калька. Голос рассказчика, речь Учителей и бытовые диалоги
   звучат по-разному.
3. **Последователен.** Один смысл термина — один перевод. Одно имя — одно написание.

Как этого добиваемся:

- **Для английского основа — старый перевод** (DEC-003): извлекаем как есть, выравниваем, редактируем.
  Заново переводим только часть IV.
- **Сначала полный цикл на одной главе**, потом масштабирование (DEC-011).
- **Глоссарий, персонажи и стайлгайд обязательны.** Самодеятельность в терминах запрещена (§9).
- **Одна основная модель-редактор**, выбранная сравнением (DEC-012). Голос держим единым.
- **Два уровня ревью:** внутреннее агентами, затем внешнее — его запускает только владелец (DEC-013).
- **Всё, что проверяется скриптом, проверяется скриптом.**
- **Ревью привязано к версии**, метрики — по подтверждённым ошибкам, статус — в одном файле (DEC-016).
- **Последнее слово за владельцем** по ключевой терминологии и стилю.

Польский переводим **с русского оригинала**. Готовый английский служит вспомогательным справочником.

## 2. Шаги и режимы работы

Работа со старым переводом разделена на три шага, которые не смешиваются (DEC-014):

| Шаг | Что можно | Что нельзя |
|---|---|---|
| **Извлечение** (`translation/legacy-en/raw/`) | техническая чистка: колонтитулы, номера страниц, склейка строк, переносы, восстановление потерянных пробелов — по координатам символов, словарь только вспомогательно и со сверкой сомнительных мест по странице (DEC-020). Каждая правка в отчёте | менять слова, пунктуацию, границы абзацев |
| **Выравнивание** (`translation/legacy-en/alignment/`, импорт в `content/en/`) | сопоставить абзацы старого перевода с ID оригинала: 1:1, 1:N, N:1, N:M, пропуски, лишнее | менять текст |
| **Литературная редактура** (`content/en/`) | всё по §6.2 | — |

Режимы литературной работы:

| Режим | Где | Что делаем |
|---|---|---|
| **Редактура** | EN: части I, II, III (все 80 глав) | доводим выровненный старый перевод до стандарта |
| **Перевод** | EN: часть IV. PL: всё | с русского с нуля; для EN — в голосе отредактированного текста |

Главный принцип редактуры: **не переписывать ради переписывания.** Верное и естественно звучащее
остаётся как есть. Глубину вмешательства задаёт стайлгайд по итогам анализа старого перевода.

## 3. Роли

| Роль | Кто | Отвечает за |
|---|---|---|
| **Владелец** | человек (хозяин репо) | ключевые термины и стиль, выбор модели, **запуск внешних ревью**, ответы на `queries`, «публикуем» |
| **Основной редактор / переводчик** | модель, выбранная на этапе 5 (до выбора подготовительную работу делает Claude в сессии) | редактура или перевод главы, предложения в глоссарий, вопросы, синопсис |
| **Координатор** | агент-сессия (Claude Code) | запуск инструментов и внутреннего ревью, разбор замечаний, подготовка пакетов для внешнего ревью, коммиты |
| **Проверки** | скрипты `tools/` | структура, длины, глоссарий, имена, типографика |
| **Внутренние ревьюеры** | агенты со свежим контекстом, **в том числе того же семейства**, что редактор | проходы по точности, терминологии и стилю (§7.2) |
| **Внешние ревьюеры** | независимые модели **другого семейства**, чем редактор (Grok, OpenAI, Gemini, … — что доступно); запускает **только владелец** | независимая проверка после внутреннего ревью |
| **Вычитчик** | человек, носитель языка (желательно) | чтение как книги, сообщения об ошибках |

## 4. Стадии главы — единственный источник: `translation/status.yml`

Стадия, режим, коммиты ревью и хеш источника хранятся **только** в `translation/status.yml`.
В шапках файлов глав статуса нет. Сайт, скрипты и агенты читают статус отсюда.

```
RU: source-ready
EN: legacy-imported → draft → checked → internal-reviewed → external-reviewed → proofread → published
```

| Стадия | Критерий |
|---|---|
| `source-ready` (RU) | глава извлечена, сверена с PDF, ID проставлены, хеш записан |
| `legacy-imported` | старый перевод извлечён и выровнен, текст **не менялся** |
| `draft` | редактура или перевод всех абзацев готовы, синопсис записан |
| `checked` | `npm run check` без ошибок, предупреждения разобраны |
| `internal-reviewed` | внутреннее ревью проведено, замечания разобраны, исправления внесены |
| `external-reviewed` | внешнее ревью проведено, замечания разобраны, **все подтверждённые `critical` и `major` исправлены и перепроверены** (§7.5, DEC-027) |
| `proofread` | человек прочитал главу, ошибки исправлены |
| `published` | владелец одобрил |

```yaml
# translation/status.yml
p1-c01:
  ru: { stage: source-ready, hash: 3f9a… }
  en:
    stage: external-reviewed
    mode: revision
    source_hash: 3f9a…                 # с какой версией RU работали
    reviews:
      - { level: internal, commit: a1b2c3d, date: 2026-10-05 }
      - { level: external, commit: d4e5f6a, reviewers: [openai-<model>], date: 2026-10-07 }
    confirmed_errors: { critical: 0, major: 7, minor: 15 }   # по resolution, не по сырым находкам
  pl: { stage: none }
```

## 5. Подготовка перед заходом (обязательный чек-лист)

Перед работой над главой `pX-cYY` на языке `LANG`:

1. Прочитать `AGENTS.md`, этот документ и `translation/decisions.md`.
2. Прочитать `translation/style/LANG.md` целиком.
3. Получить глоссарий и персонажей для главы: `npm run glossary pX-cYY LANG`. Пока скрипта нет —
   прочитать `translation/glossary.yml` и `translation/characters.yml` целиком.
4. **Термины главы:** если в главе есть понятия, которых нет в глоссарии, — предложить их (§9) до
   или во время работы над главой.
5. Прочитать `translation/synopsis/part-X.md` до текущей главы.
6. Прочитать последние ~20 абзацев предыдущей главы на `LANG`.
7. Проверить `translation/queries/LANG/` на ответы владельца.

## 6. Работа над главой

### 6.1. Общие правила

1. Работать **кусками по 1 500–2 500 слов оригинала**, по границам абзацев. Предыдущий готовый кусок
   держать в контексте.
2. Каждый ID оригинала покрыт ровно один раз и по порядку (правила ID — ARCHITECTURE §3). Ничего не
   пропускать, не добавлять пояснений в текст (сноска — только если разрешено стайлгайдом).
3. Термины и имена — строго по глоссарию (§9). Новое → `proposed`, не молчаливая импровизация.
4. Тёмное место или возможная опечатка в оригинале → вопрос в `translation/queries/LANG/pX-cYY.md`
   (ID абзаца, цитата, варианты, рекомендация). В тексте — лучший вариант, без заглушек.
5. После главы: `npm run check`, синопсис главы, обновление `status.yml`, коммит (§12).

### 6.2. Режим «Редактура»

Для каждого абзаца сравнить выровненный старый перевод с оригиналом и:

- **оставить**, если смысл верен, термины по глоссарию и текст читается естественно;
- **исправить** ошибку смысла, пропуск или добавление, нарушение глоссария (*duke* → *prince*),
  мешающую кальку, грамматику;
- **не трогать** вкусовые мелочи, если они не противоречат стайлгайду;
- там, где выравнивание дало N:1 или 1:N, **по возможности привести к 1:1**, если это не портит текст.

Масштаб изменений виден в `npm run compare pX-cYY` (RU | старый EN | новый EN с подсветкой) и в git-диффе.
Доля изменённых абзацев — метрика, которая показывает, не уходит ли редактура в переписывание.

### 6.3. Режим «Перевод»

С русского с нуля. Для английской части IV — сначала мини-пилот: несколько страниц сравниваются
с отредактированными главами, владелец одобряет голос.

## 7. Ревью: два уровня

### 7.1. Порядок

```
draft → checked → внутреннее ревью → разбор и исправления → commit + push
      → пакет для внешнего ревью → владелец запускает внешние модели → разбор и исправления
      → повторная проверка серьёзных исправлений → external-reviewed
```

Внутреннее ревью **не заменяет** внешнее. Внешнее проводится для каждой главы (или пачки глав, §7.6).

### 7.2. Внутреннее ревью (агенты)

- Запускает координатор. Каждый проход — **отдельный агент со свежим контекстом**, без доступа
  к рассуждениям редактора. Можно модели того же семейства.
- Возможные проходы:
  1. **Точность** — сверка с RU по абзацам: смысл, пропуски, добавления.
  2. **Терминология и согласованность** — глоссарий, имена, обращения, связь с соседними главами.
  3. **Язык и стиль** — ревьюер сначала читает только английский, как читатель. Но каждое его
     предложение **перед принятием сверяется с RU**: стилистическая правка не должна менять смысл.
- **На пилоте — все три прохода**, и для каждого считается, сколько подтверждённых замечаний он добавил
  сверх остальных. По итогам фиксируется достаточная схема (DEC-021): например, один общий ревьюер для
  обычных глав и отдельные проходы для сложных (плотные поучения, стихи, главы с новыми терминами).
  Схема записывается сюда и в `decisions.md`.
- Результат: `translation/reviews/LANG/<unit>/internal-<проход>-<YYYYMMDD>.json` в формате §7.4.
- Разбор (§7.5) и исправления до подготовки внешнего пакета.

### 7.3. Внешнее ревью (владелец)

Внешние модели **запускает только владелец** (DEC-005, DEC-013). Внешний ревьюер — из **другого семейства**,
чем основной редактор (например, редактор Claude → ревьюер OpenAI или Grok).

Координатор:

1. Коммитит текст после внутреннего ревью и **пушит**.
2. Готовит пакет `translation/reviews/LANG/<unit>/request.md` (большую главу делит на
   `request-1.md`, `request-2.md`, чтобы каждый влез в окно модели). В шапке пакета:
   ```yaml
   unit: p1-c01
   lang: en
   commit: a1b2c3d            # коммит, в котором зафиксированы текст И правила (глоссарий, стайлгайд, промпты)
   text_hash: …               # хеш главы — ответ можно проверить на соответствие версии
   source_hash: …             # хеш RU-главы
   ```
   Дальше в пакете: цель, на что смотреть в первую очередь, выдержка из стайлгайда, подмножество глоссария,
   таблица `ID | RU | EN`, **список терминов, требующих явного вердикта** (§9), формат ответа (§7.4).
   Результаты внутреннего ревью во внешний пакет **не включаются** — внешний взгляд должен быть независимым.
3. Коммитит пакет, пушит и **останавливается**. В чат владельцу:
   - что готово (коммит, путь к пакету);
   - **стартовый промпт**, готовый к копированию: кто ты, что ревьюим, цель, критерии, формат ответа,
     «пакет приложен ниже»;
   - сколько внешних ревьюеров нужно и из каких семейств.
4. Ждёт. Ответ владелец вставляет в чат или кладёт файлом
   `translation/reviews/LANG/<unit>/external-<vendor>-<model>-<YYYYMMDD>.json`. Если ответ вставлен в чат,
   координатор сохраняет его сам. Ответ, в котором указан не тот `commit`, разбирается с осторожностью:
   замечания сверяются с текущим текстом.

### 7.4. Формат замечаний (оба уровня)

JSON (можно внутри блока кода в ответе модели):

```json
{
  "unit": "p1-c01",
  "lang": "en",
  "commit": "a1b2c3d",
  "reviewer": "openai-<model>",
  "level": "external",
  "findings": [
    {
      "id": "p1-c01-042",
      "category": "omission",
      "severity": "major",
      "source_excerpt": "…но не мог сказать ни слова",
      "target_excerpt": "…but said nothing",
      "suggestion": "…but could not utter a single word",
      "rationale": "‘не мог’ — невозможность, а не выбор"
    }
  ],
  "terms": [
    { "term_id": "samoobladanie", "lang": "en", "verdict": "agree" },
    { "term_id": "dacha",         "lang": "en", "verdict": "object", "suggestion": "country house", "rationale": "…" },
    { "term_id": "mir.peace",     "lang": "en", "verdict": "unsure", "rationale": "…" }
  ],
  "overall": { "accuracy": 4, "fluency": 4, "style": 3, "comment": "…" }
}
```

Категории: `mistranslation`, `omission`, `addition`, `terminology`, `name`, `fluency`, `style`, `register`,
`grammar`, `typography`. Серьёзность: `critical` (искажён смысл, пропущено важное), `major` (заметная
неточность или корявость), `minor` (вкусовое, мелочь).

По **каждому** термину из списка — вердикт `agree` / `object` / `unsure`. Термин без вердикта считается
неподтверждённым (§9).

### 7.5. Разбор, повторная проверка, метрики

1. Свести отчёты единицы, склеить дубликаты.
2. По каждому замечанию — решение в `translation/reviews/LANG/<unit>/resolution.md`:
   `accept` / `accept-modified` / `reject` + причина одной строкой. Отклонённое `critical` или расхождение
   ревьюеров по смыслу → в `queries` владельцу.
3. Если замечание касается термина или стиля — обновить глоссарий или стайлгайд и проверить другие главы.
4. **Повторная проверка:** все принятые `critical` и `major` после исправления проверяет отдельный
   агент со свежим контекстом: исправлено ли и не внесено ли новой ошибки. Для `critical` из внешнего
   ревью координатор готовит владельцу короткий пакет повторной проверки (только эти абзацы) тому же
   внешнему ревьюеру. Отправлять ли его, решает владелец.
5. **Метрики — только по подтверждённым ошибкам** (`accept` + `accept-modified`) на 1 000 слов, по уровням
   серьёзности и по уровню ревью (сколько нашло внутреннее, сколько добавило внешнее). Сырые счётчики
   находок вспомогательны. Итоги — в `status.yml` (`confirmed_errors`).
6. **Критерий готовности (DEC-027):** все подтверждённые `critical` и `major` исправлены и перепроверены, какой бы ни была
   плотность; подтверждённые `minor` исправлены, отклонённые — с причиной. Ориентир «0 critical и не больше 1 major на
   1 000 слов» относится к **первому** ревью отредактированного текста: он показывает, хорошо ли работает редактура
   (превышение → правим промпт, стайлгайд или усиливаем внутреннее ревью), и не разрешает оставлять ошибки.

### 7.6. Сколько внешних ревьюеров

- **Анализ старого перевода, ядро глоссария, пилот, главы с плотными поучениями Учителей:** два внешних
  (если доступны), иначе один.
- **Остальное:** один внешний. Когда метрики стабильны (внешнее ревью почти ничего не добавляет к
  внутреннему), — пачками по несколько глав.
- Внешнее ревью добавляет много подтверждённых ошибок → усиливаем внутреннее ревью и правим стайлгайд.

## 8. Синопсис — память проекта

`translation/synopsis/part-N.md` — краткое содержание по главам: заголовок, 5–10 предложений,
новые персонажи и понятия с ID первого появления. Пишется после каждой главы.

## 9. Глоссарий и персонажи — никакой самодеятельности

Схема утверждения — вариант Б (DEC-002) с уточнениями DEC-015.

### 9.1. Уровни и утверждение

| Уровень | Что входит | Кто утверждает |
|---|---|---|
| `core` | понятия учения, имена персонажей, титулы, обращения, повторяющиеся формулы | **только владелец** |
| `secondary` | бытовые реалии, топонимы, предметы, эпизодические персонажи | автоматически, **если хотя бы один внешний ревьюер явно ответил `agree` и никто не ответил `object`**. Молчание или `unsure` — не согласие: термин остаётся `proposed` |

- Утверждение **раздельное по языкам**: `en` утверждён — не значит, что утверждён `pl`.
- Сомневаешься в уровне — ставь `core`.
- Внутренние ревьюеры тоже дают вердикты, но для автоутверждения засчитываются только внешние.

### 9.2. Правила

1. **Утверждённое обязательно.** Менять его может только владелец. Замена идёт скриптом по корпусу,
   запись — в `decisions.md`.
2. **Первый вариант держится.** Пока `proposed` не утверждён, все используют именно его.
3. **Дубли запрещены.** Две записи с одинаковыми `ru` и `sense` — ошибка проверки.
4. **Разные значения — разные записи.** Одно русское слово с разными смыслами («мир» — мир-покой и
   мир-вселенная, «свет» — свет и высший свет, «брат» — родной брат и брат по Братству, «дух»,
   «учитель» / «Учитель») заводится отдельными записями `ru#sense` с описанием, как их различать.
   Проверка для многозначных слов не падает, а выдаёт напоминание сверить значение.
5. **Каждая запись с контекстом:** `first_seen` (ID абзаца) и `note`.
6. **Для английского по умолчанию берётся вариант старого перевода** (`en_legacy`), если он не ошибочен.
7. **Поглавный рост:** до пилота утверждается только ядро и термины выбранных глав (DEC-011). Термины
   каждой следующей главы проходят подтверждение в её цикле ревью.

### 9.5. Известные вопросы (этапы 2–3)

| Вопрос | Старый перевод | Проблема | Рекомендация |
|---|---|---|---|
| «И.» (Иллофиллион) | «I.», «with I.», «I.'s» | сливается с местоимением *I* | «Il.» или полное «Illofillion», решить |

| Инициалы: «в К.», «в Б.», «капитан Т.» | сохранены | стиль эпохи | сохранить |
| Вариант английского | британский с оксфордским *-ize* | *gotten* (американизм) | британский с *-ize*, окончательно (DEC-024) |
| Ты/вы | теряется | — | в EN — тоном и лексикой; в PL — *ty / Pan, Pani* |
| Кавычки в диалогах | “…” | RU — тире | EN — “…”; PL — решить в стайлгайде |

## 10. Сравнение моделей и смена модели (DEC-012)

- **Основной редактор выбирается слепым сравнением** на калибровочном наборе (4–5 характерных отрывков,
  PLAN, этап 5): одинаковые промпт, стайлгайд и глоссарий; варианты обезличены (A/B/C…); критерии — точность,
  глоссарий, бережность к старому тексту, качество языка; учитывается практичность запуска.
- Дальше **одна основная модель на язык**. Внешние ревьюеры — из другого семейства.
- **Смена модели** (новая версия, другой вендор) — только через калибровку: прогон калибровочного набора и
  одной уже готовой главы, сравнение с принятым голосом, правка промпта или стайлгайда. Решение фиксируется
  в `decisions.md`.
- Промпты — в `translation/prompts/`, версионируются. Меняли промпт — отмечаем в `decisions.md`.
- Ключей API в репозитории нет. Если основной редактор вызывается по API, ключ владельца хранится
  в переменной окружения вне репозитория.
